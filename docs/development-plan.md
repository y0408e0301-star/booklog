## 1. 本書の目的

どの順番で作るか（段階）と、1 つの Pull Request で何を作るかを決め、いまどこまでできたかが分かるようにする。何を作るかは[要件定義書](requirements/requirements.md)と[機能定義書](functions/function-definition.md)、どう作るかは[基本設計書](design/basic-design.md)と[技術スタック定義書](tech-stack.md)で決めている。

## 2. 進め方の方針

**機能ごとに、API（バックエンド）とそれを使う画面（フロントエンド）を 1 つの Pull Request で作る。**

| 段階 | 作るもの | 理由 |
| --- | --- | --- |
| 段階 1 | 土台と、機能ごとの API と画面（FN-01〜FN-11、G-1〜G-13） | 1 つの機能を API のテストで固めたら、すぐに本物の API につないだ画面で確かめられる。画面で見つけた問題を、同じ Pull Request の中で API に直せる |
| 段階 2 | 通しのテストと公開、受け入れ | 登録 → 本を探す → レビュー → 参考になった・コメント → フォロー → 本棚 の流れを画面から確かめ（N-28）、AWS に公開して検収する（P-5・13 章） |

Raise timeline で後から足したもの（API の仕様書・層ごとの単体テスト・構造化ログ）は、最初から入れる。後から足すと、それまでに作ったコードを全部見直すことになったため。

| もの | BookLog での入れ方 |
| --- | --- |
| API の仕様書（OpenAPI。基本設計書 2.1） | 1-1 で仕組みを入れ、各機能の行で API と一緒に仕様書と画面の型を更新する |
| 層ごとの単体テスト | 各機能の行で、API を通したテスト（MockMvc・Testcontainers）に加えて、Controller・Service・Repository（画面は関数・hook・部品）を 1 つずつ確かめるテストも書く |
| 構造化ログ（基本設計書 2.3） | 1-1 で入れる。Google Books API の呼び出しのログは 1-3 で足す |

- 機能どうしの関係で、ある機能の画面の一部が後の機能の API を使うときは、その API を作る行で画面も仕上げる（例：G-5 の読書ステータスのボタンは 1-7）。それまでの画面は、その機能で確かめられる範囲だけを出す
- 動きは、API のテスト・画面のテストと、本物の API につないだ画面（Chrome DevTools。375px の幅も）で確かめる。書籍検索は開発用の API キーで本物の Google Books API につなぐ（1 日の上限に気をつける）

## 3. 作る順番

1 行を 1 つの Issue・1 つの Pull Request にする。終わったら、その Pull Request の中で「状態」を ✅ にする。

状態：✅ 終わった、▶ 作業中、空欄 まだ

- 「フォロー中」タブはフォロー（1-10）がないと中身を確かめにくいが、表を作ってテストのデータを入れれば確かめられるので、follows の表は 1-5 で作る。1-10 ではフォローする操作を作る
- 定期の処理（1 日 1 回の 4:30）は、最初に要る 1-1（期限切れのリフレッシュトークンの削除）で仕組みを作り、1-3（古い検索の結果・呼び出し回数の削除）と 1-6（S3 から消せなかった写真の消し直し）で処理を足す
- 退会（1-12）は、すべての表ができてから作る。ほかの行で表を足すときは、ユーザーの外部キーを ON DELETE CASCADE にしておく（データ設計書 方針 7）

## 5. 進め方の決まり

- 開発のルール（Issue → ブランチ → Pull Request → squash マージ）は [CONTRIBUTING.md](../CONTRIBUTING.md) のとおり
- 作っている途中で仕様を変えるときは、同じ Pull Request で文書も直す（[CLAUDE.md](../CLAUDE.md)）
- 順番を変えるときや、行を分ける・まとめるときは、本書の版数を上げて改訂履歴に書く
- push の前に、API の `mvnw verify` と画面の lint・テスト・ビルドを手元で全部流し直す（Raise timeline で、テストを足した後に lint を流し忘れて CI で落ちたため）
- 確認のために開発用のデータベースに作ったユーザーなどは、確かめ終わったら消す
